# 信息源取法

目标：用最少 token 拿到「我做了什么、做成了什么」的证据，不读别人的话，不读无关内容。

## 1. AI Agent 会话（第一顺位）

为什么排第一：你 80% 的真实工作指令和拍板都留在这里，而且只有你这一侧的意图，噪音最低。

常见工具与目录：

| 工具 | 路径 | 格式 |
|---|---|---|
| Codex | `~/.codex/sessions/**/*.jsonl`、`~/.codex/archived_sessions/*.jsonl` | 每行一条 `response_item`，user 消息在 `payload.content[].text` |
| Claude Code | `~/.claude/projects/**/*.jsonl` | 每行一条，`type: user/assistant`，`message.content` |
| Cursor | `~/.cursor/projects/**/*.jsonl` | 同上结构，近似 Claude Code |
| 其他自带存储的 Agent | 看它自己的 session 目录 | 抓到「role + text + timestamp」即可 |

做法：

```bash
python3 scripts/scan_agent_sessions.py \
  --start 2026-10-26 --end 2026-11-02 \
  --output /tmp/sessions.json
```

脚本会统一输出：`{session, cwd, messages:[{timestamp, role, text}]}`。一条会话里可能涉及多个项目，按内容归类，不要按会话归类。

取用规则：

- **只信 user 消息**判断「我发起/要求/拍板了什么」。
- assistant 的**最终答复**只用来确认产出是否存在，不能把 Agent 自己提的建议算成你的工作。
- 中断、失败、只讨论未执行的，不写成完成。

## 2. 本人发送的消息（用来确认「推动」和「对外承诺」）

只取你自己发的，不要引用他人正文——既省 token 也避免抢功。

```bash
python3 scripts/digest_own_messages.py \
  --start 2026-10-26T00:00:00+08:00 \
  --end 2026-11-02T00:00:00+08:00 \
  --output /tmp/my_messages.json
```

要点：

- 「好的 / 收到 / 表情」不单独构成成果；只有能挂到某个项目上的确认才有意义。
- 你发出去的需求、方案、结论、排期、评审意见，是「推动」类条目的最佳证据。
- 你发出去的材料（zip、文档链接、数据）本身就是交付物证据。

## 3. 会议转写 / 纪要

- 有转写的（妙记、录音、会议纪要）导出成 txt，交给 Agent 读，让它输出「结论 / 分歧 / 待办 / 谁负责」。
- 只有你能引用自己的发言和会上明确拍板的内容；别人的发言只作背景。
- 会上定了但还没落文档的，写「X 会定下 Y 方向」，不要写成「完成 Y」。

## 4. 本地交付物（最硬的证据）

```bash
find . -type f -newermt '2026-10-26' ! -newermt '2026-11-02' \
  ! -path './node_modules/*' ! -path './.git/*' | head -50
```

- 只看文件名、首段标题、修改时间，不要递归读代码、依赖、构建产物。
- 一个交付物经常能覆盖一条周报（需求文档、原型、截图、报告、上线日志）。
- 交付物的状态要单独核实：文件在 ≠ 已上线。

## 5. 项目跟踪系统（只核对，不推断）

- 只查当前状态、负责人、编号。
- 「开发中 / 测试中 / 已关闭」都不能自动等于「已完成」，除非有发布记录或本人确认。
- 不确定就写「待核实」，这比写错强。

## 取源顺序的反直觉之处

先取会话，再取消息，最后取交付物——因为交付物只有文件、没有意图。反过来做，你会写出一堆「有文件但不知道为什么做」的条目。
